# SPEC-DRIVEN DEVELOPMENT (SDD) WORKFLOW
# AI Assistant #1 (planning) + AI Assistant #2 / Cursor (coding) — Complete Guide
 
A structured method for building software with AI pair-programming tools.
AI Assistant #1 (Claude, ChatGPT, Gemini, etc.) handles planning, specifications, and documentation.
AI Assistant #2 (your Cursor-integrated model) handles code generation inside your editor.
 
---
 
## STAGE 0: Choose Your Rigor Level (Do This First, Every Time)
 
Not every change deserves the full workflow below. Before opening APP-OVERVIEW.md,
answer one question: **does this change need Structured/Formal SDD, or is a
lightweight prompt enough?**
 
This isn't a loophole — it's part of the discipline. Running full SDD on a
one-line bug fix wastes more time than it saves and clutters your repo with
specs nobody will ever reread. Skipping SDD on a multi-file, client-facing
feature is how you end up with the exact problems this workflow exists to
prevent.
 
```
LIGHTWEIGHT (a prompt is enough — no separate SPEC file):
□ Prototype, throwaway exploration, or a UI sketch you expect to redo
□ Single-file change, or under ~20 lines
□ One-off bug fix with an obvious, narrow cause
□ Nobody but you will ever read this code
→ Just describe the change to AI Assistant #2 directly and iterate.
 
STRUCTURED (this workflow, starting at Stage 1):
□ Multiple files or components touched
□ Behavior other features will depend on
□ Correctness matters more than speed
□ You'll want to remember why this was built this way, in 3+ months
→ Full SPEC-001, prompts, implementation, validity review.
 
FORMAL (Structured, plus extra rigor):
□ Client-facing or production-bound
□ High-risk (money, auth, data integrity)
□ Multiple people (or multiple AI sessions) need to stay coordinated
□ Smart contracts, or anything that holds or authorizes on-chain value
  (add Appendix A at the end of this document)
→ Everything in this workflow, plus don't skip Stage 5 or Stage 7.
```
 
If you're unsure which bucket you're in, default to Structured. The cost of
over-specifying a simple feature is a wasted 20 minutes. The cost of under-
specifying a complex one is a rewrite.
 
---
 
🧠 Why this gate exists
 
Structure has a real cost, not just a real benefit. A Spec Kit-style workflow
can produce more Markdown than code for a small feature — and every extra
document is something you have to read, correct, and keep in sync. The
question isn't "should I always use SDD" or "should I never use SDD" — it's
"how much ceremony does *this specific change* actually need?"
 
Treat this as a spectrum, not a binary switch. A short paragraph describing
intent before you prompt AI Assistant #2 still counts as SDD-in-spirit — you
thought before you coded. The full Stage 1-8 workflow is for when the stakes
or the complexity justify the overhead. Most projects live somewhere in the
middle, and the judgment call is yours to make consciously, not by default.
 
---

## STAGE 0.5: Create Steering Files (Once Per Project)
 
APP-OVERVIEW.md changes per feature. Some things about your project don't —
what it is, what stack it runs on, how code is conventionally written, and
which architectural rules are non-negotiable. Bundling that durable context
into every APP-OVERVIEW.md means restating it every time, and it drifts out
of sync the moment one SPEC updates a convention and the others don't.
 
Create these once, at project start, in `docs/steering/`:
 
```
docs/steering/
  product.md        # what the product is, who it's for, what it is NOT
  tech-stack.md      # the stack, versions, and WHY each major choice was made
  conventions.md     # naming, error shapes, code patterns beyond the linter
  principles.md      # non-negotiable architectural rules, one line each
  decisions.md       # architecture decisions (ADR-lite, append-only); created
                     # by Step 1.2d rather than drafted here
```
 
Prompt for AI Assistant #1:
```
Based on our conversation about [project], draft the four steering files:
 
1. product.md — value proposition, target audience, and an explicit
   "What This Product Is NOT" section (as important as what it is).
2. tech-stack.md — the stack with a one-sentence WHY for each major
   choice. Not a dependency list — a rationale. "PostgreSQL because
   transaction records need ACID guarantees" is the sentence that stops
   a future session from suggesting SQLite.
3. conventions.md — naming conventions, error response shape, how auth
   is applied at the boundary, and which language style guide this
   project follows (e.g. PEP 8 for Python, Airbnb or Standard for JS/TS,
   Google Java Style Guide) — name it explicitly, don't leave it implied.
   Also note any deliberate deviations from that guide and why. This is
   the tacit patterns an experienced developer on this team would
   already know.
4. principles.md — the shortest file. Load-bearing rules in declarative
   sentences: "All money math is integer arithmetic, never float."
   "No direct database access outside the repository layer." "If
   uncertain whether something is in scope, it is not."
```
 
---
 
🧠 Why steering is separate from the master document
 
APP-OVERVIEW.md answers "what are we building this feature/version?" Steering
answers "what is true about this project regardless of which feature we're
on?" Collapsing them means every new SPEC either re-derives the tech stack
rationale from scratch or silently assumes AI Assistant #1 remembers last
month's conversation — which it doesn't.
 
Steering files change rarely, and only when you make a deliberate
architectural decision — never for a single feature. When they do change,
that decision becomes every future session's default context, not something
re-argued each time. `principles.md` is the highest-leverage file here: one
line like "no direct database access outside the repository layer" prevents
a category of error before AI Assistant #2 generates a single line, in every
SPEC from here forward.
 
One precedence rule: steering does not silently override an approved SPEC.
If steering conflicts with an already-approved SPEC, stop and ask which one
should change — don't let AI Assistant #2 quietly pick one.

## STAGE 1: Create the Application Document (The Master Plan)
 
---
 
### Step 1.1: Describe Your Idea to Your AI Assistant
 
What you do:
Open AI Assistant #1 and describe your app in plain language — like explaining it to a friend.
 
Example:
  "I want to build a web app for tracking personal finances. Users can:
  - Add income and expense transactions
  - See statistics broken down by category
  - Set monthly budgets
  - Get alerts when they go over budget
  The app will run in a browser and store data in a database."
 
---
 
🧠 What AI Assistant #1 is doing here — and why it matters
 
AI Assistant #1 is acting as a senior developer interviewing you about your project before writing a single line of code. This is called requirements gathering, and professional teams do it before every project.
 
Why? Because the most expensive bugs aren't syntax errors — they're building the wrong thing. Discovering that you need multi-user support after building a single-user system means rewriting your entire authentication layer. Ten minutes of clear thinking now saves ten hours of rework later.
 
Every question AI Assistant #1 asks is protecting you from a future problem.
 
---
 
### Step 1.2: AI Asks Clarifying Questions
 
AI Assistant #1 will ask something like:
 
  "Let me ask a few things to build a complete overview:
 
  1. Users & Authentication:
     - Do users need to register and log in?
     - Single accounts, or shared family accounts?
 
  2. Data & Storage:
     - How much history to keep? (1 year, forever?)
     - Cloud database or local storage?
 
  3. Technology Stack:
     - Any preferences? (Python, JavaScript, etc.)
     - Web app only, or also mobile?
 
  4. Scale:
     - Just for you, or for many users?
     - Roughly how many transactions per month?
     - What does growth look like in a year — same scale, 10x, 100x?
     - Is there a specific bottleneck you're worried about (data volume,
       concurrent writes, request rate)? If unsure, say so.
 
  5. Feature Priority:
     - What's the minimum version that's useful (MVP)?
     - What can wait for version 2?
 
  6. Non-Goals:
     - What are you deliberately NOT building in this version?
     - Are there tempting features you want to explicitly rule out now,
       so they don't creep in later?"
 
Answer as best you can. If you don't know — say so. The AI will suggest a sensible default.
 
---
 
🧠 What AI Assistant #1 is doing here
 
It's mapping your vague idea onto concrete technical decisions. Each question corresponds to an architectural choice:
 
- "Cloud or local?" → SQLite vs. PostgreSQL vs. Firebase
- "Single user or many?" → whether you need authentication at all
- "Mobile too?" → whether you need an API layer or can use server-side rendering
- "What does growth look like?" → whether today's simplest solution survives
  next year, or whether you're deliberately building throwaway scaffolding
 
These aren't bureaucratic questions. They determine which technology decisions get locked in early — and which ones can change later. AI Assistant #1 is building a mental model of your system before committing anything to paper.
 
Non-Goals deserve special attention: it's tempting to fold them into a vague
"out of scope" line, but a named, bulleted Non-Goals list does something a
paragraph doesn't — it gives the AI a concrete boundary it can check itself
against later. "No custom aliases" or "No bank account integration" is
something Cursor can actually notice it's about to violate mid-implementation.
"Keep it simple" is not.
 
Boundaries go one level more granular than Non-Goals: Non-Goals says what
you're not building this version. Boundaries says what Cursor can decide on
its own mid-task versus what needs your sign-off first. A flat list of "never
do X" rules misses the middle ground — most real risks aren't "always safe"
or "always forbidden," they're "usually fine, but check with me first." That
middle tier (⚠️ Ask first) is what a binary always/never list can't express,
and it's where most silent scope creep and unreviewed schema changes actually
happen.
 
The scale question specifically guards against a common trap: a design that's
perfectly reasonable at "10 users for myself" can quietly become the wrong
architecture at "10,000 users for a client" — and nobody notices until it's
expensive to unwind. Answering "10x growth is out of scope for this version"
is a completely valid answer — it just needs to be a *decision*, not an
accident.
 
---
 
### Step 1.2c: Elicitation Technique (Real Stakeholder or Simulated)
 
Step 1.2's question list works whether or not there's a real stakeholder
behind it. Handle each case differently.
 
**When there's a real stakeholder** (a client, a colleague, a teacher who
requested the feature): AI Assistant #1's questions are a starting point,
not the whole interview. Four habits sharpen what you get back:
 
- **Start concrete, not abstract.** "What do you need?" invites a vague
  answer. Showing a current screen, a mockup, or a recent example gets a
  specific one.
- **Ask what breaks today, and what they do instead.** Workarounds are
  where unspoken requirements hide — a spreadsheet someone maintains on
  the side because the current system doesn't do something is a
  requirement nobody stated out loud.
- **Restate what you heard, in their words, before moving on.** This is
  the cheapest way to catch two people leaving a conversation thinking
  they agreed, having understood different things.
- **Treat what's said as a claim to verify, not a requirement to record
  verbatim.** People often describe the process they're supposed to
  follow, not the one they actually follow. Two stakeholders can each
  accurately describe wanting things that can't both be true.
 
**When there's no real stakeholder** (a solo project, an exploratory tool,
research work with no client to interview): AI Assistant #1 can simulate
the elicitation instead of skipping it. Prompt:
 
```
Before we write APP-OVERVIEW.md, role-play as [target user persona] being
interviewed about this idea. Ask the kinds of questions a real user in
that role would raise — pain points, workarounds they'd currently use,
edge cases specific to that domain. Draw on what you know about this
domain generally. Then switch back to planning mode and fold anything
genuinely useful into the clarifying questions.
```
 
This surfaces domain-shaped questions you might not think to ask alone —
but it is a simulation grounded in general domain knowledge, not real user
data. Label anything it produces as a hypothesis, not a validated
requirement, and say so explicitly in APP-OVERVIEW.md if a Non-Goal or
a feature decision came from this exercise rather than a real
conversation. Confusing a simulated persona's guess with an actual user's
stated need is how a Non-Goals list ends up excluding something a real
user would have wanted.
 
---
 
🧠 Why simulated elicitation earns a place here, carefully
 
The risk is obvious: an AI role-playing a user is not a user, and treating
its output with the same confidence as a real interview manufactures false
certainty about requirements nobody actually validated. The value is real
too — a domain-knowledgeable model raising "what happens when two students
submit conflicting swap requests for the same time slot?" for a course-
scheduling tool is a genuinely useful prompt for your own thinking, even
though it's a guess, not a fact. Use it to generate candidate questions to
think about, never as a substitute for asking a real person when one
exists.
 
---
 
### Step 1.2b: Architecture Decision Point (Human Judgment Required)
 
Before AI Assistant #1 writes APP-OVERVIEW.md, ask explicitly for options —
don't let the AI silently pick one architecture and hand you a finished document.
 
Prompt for AI Assistant #1:
```
Before you draft APP-OVERVIEW.md, give me 2–3 architectural approaches
for this project. For each one:
1. What it is (one sentence)
2. The named architectural style it corresponds to (e.g. layered,
   modular monolith, event-driven, client-server, microservices, or one
   of pipes-and-filters / broker / peer-to-peer / plugin) — name it
   explicitly, don't just describe the shape without the label
3. What it optimizes for
4. What it costs you (complexity now, or flexibility later)
5. When you'd regret choosing it
 
Don't recommend one — lay out the trade-offs and let me choose.
```
 
Example output for the Personal Finance Tracker:
```
Option A — Monolith (Flask + SQLite, everything in one app)
  Style: Modular monolith, layered internally
  Optimizes for: speed to MVP, one person maintaining it
  Costs: harder to scale to multiple services later; SQLite doesn't
  handle concurrent writes well past a few simultaneous users
  Regret it if: you add a second developer, or usage grows past
  "personal tool" into "small team tool"
 
Option B — Modular monolith (Flask + PostgreSQL, clear service boundaries
  inside one codebase — auth/transactions/budgets as separate modules)
  Style: Modular monolith, stricter internal layering than Option A
  Optimizes for: room to grow without a full rewrite
  Costs: more boilerplate now, more upfront design decisions
  Regret it if: the project never grows past personal use — you paid
  a complexity tax for flexibility you didn't need
 
Option C — API-first (separate backend API + any frontend)
  Style: Client-server, with the backend exposed as a service
  Optimizes for: mobile app later, multiple frontends
  Costs: more moving parts from day one; overkill if it's just a
  personal web tool
  Regret it if: you never build the mobile app you were planning for
```
 
You pick one, and — critically — **write down why**, not just which one:
 
```
## Architecture Decision
Chosen: Option A — Monolith
Reason: single developer, personal use, MVP timeline is 5 weeks.
Revisit if: usage grows past ~5 concurrent users, or a second
developer joins the project.
Migration path: [the first concrete step if the trigger fires — e.g.
SQLite -> PostgreSQL: swap driver, run migrations, re-run Performance
Verification]
```
 
This goes into APP-OVERVIEW.md as its own section (see Step 1.3, Section 3).
 
---
 
🧠 Why this step exists — and why it can't be skipped
 
This is the single most consequential moment in the whole workflow, and it's
also the moment easiest to sleepwalk through. Without this step, AI Assistant #1
picks *an* architecture (usually a sensible default) and writes it straight
into APP-OVERVIEW.md — you approve it by doing nothing, not by deciding.
 
That matters because architectural decisions are exactly the ones with
long-payoff, hard-to-see-now consequences. A monolith is genuinely the right
call for a five-week solo MVP — but it's a decision that should be made
*because* you're a solo developer on a five-week timeline, not because it
was the first thing the AI suggested. If the project's shape changes later
(a client wants it productionized, a second developer joins), you want a
written "Revisit if:" trigger, not a vague memory of "I think we just went
with whatever Claude suggested."
 
The habit of writing down the *reason*, not just the choice, is what makes
this defensible later — identical to why DATA-DECISIONS.md matters in the
data analysis workflow. A choice without a documented reason is indistinguishable,
six months later, from an accident.
 
---
 
### Step 1.2d: Architecture Brief (How the Hard Parts Work)
 
Step 1.2b picks the overall shape (monolith, modular monolith, API-first).
It does not say how the hard parts work inside that shape: what happens when
two requests collide, what must never be lost, what happens when a
dependency is down. These are the decisions that are expensive to reverse
once code exists, and the ones AI Assistant #2 will otherwise settle silently inside
a SPEC. Do this once per project, after Step 1.2b and before the master
document is finalized. Repeat it for any feature that adds an external
dependency, a new owner of some data, or new concurrency.
 
Prompt for AI Assistant #1:
```
Using the Scale answers, the chosen architecture and the core use cases,
produce a one-page Architecture Brief:
 
1. Non-functional targets, with numbers: users and data volume now and in
   a year, the response-time target for the main operations, availability
   expected, and what must never be stale or lost. "Fast" and "scalable"
   are not targets. If I do not know a number, propose a default and
   mark it as an assumption.
2. Data model: the entities, which single component owns (writes) each
   one, the invariants that must always hold (e.g. "a seat is sold at
   most once"), and which copy of any data is the source of truth.
3. The hardest 1-2 requirements (usually concurrency, consistency or an
   external dependency): two or three ways to meet each, the trade-off of
   each, and the one chosen, with the reason. Do not recommend silently;
   let me choose.
4. Boundaries and failure modes: for every external system and every
   component boundary, what happens when it is down, slow, returns bad
   data, or is called twice at the same moment? Name the behavior (retry,
   fail, queue, show an error) and who is responsible for it.
5. Record each decision in the ADR-lite format below. Do not add
   components, services or technologies that no requirement in items 1-4
   needs.
```
 
Each decision goes into `docs/steering/decisions.md` (append-only):
 
```
## D-001: [short title]            Status: Accepted | Superseded by D-00N
Context:      [the requirement or constraint that forces a choice]
Decision:     [what was chosen]
Rejected:     [alternative - why not, one line each]
Consequences: [the cost accepted]. Revisit if: [the concrete trigger]
```
 
Rules for the file: entries are never deleted or rewritten; a changed
decision gets a new entry and the old one is marked Superseded. An
Accepted decision binds the SPECs like a steering file does: if a SPEC
or AI Assistant #2 wants to contradict one, stop and ask, never reverse it quietly.
 
Optional but cheap: before you approve the brief, show it to a different
model with the prompt "Find where this design fails at 10x volume, under
two simultaneous writes to the same record, and when each external
dependency is down." Treat its answers as hypotheses to check, not as
corrections to apply.
 
Tier: Lightweight skips this. Structured does items 1, 2 and 4, plus a
decisions.md entry for every choice that would be expensive to reverse.
Formal does all five and records the review in `docs/DESIGN.md`.
 
---
 
🧠 Why this is separate from Step 1.2b and from the Design Sequence
 
Step 1.2b answers "what shape?" The Design Sequence answers "which
entities, components and operations?" Neither forces a number onto "scalable"
or a behavior onto "what if the payment provider times out". Those gaps
are where a design that looks fine in review fails in production: two
people book the last seat at the same moment, a retried request charges
twice, a dependency outage takes the whole app down. Putting targets,
invariants and failure behavior on one page, with the reasons recorded,
turns them into decisions someone made, rather than defaults the code
happened to contain. It is also what stops a later session from re-arguing
or silently contradicting a choice, since decisions.md is part of the
context every session starts from.
 
It stays small on purpose: one page, no extra components, and nothing that
a stated requirement does not need (see Common Mistake 3 on over-building).

### Step 2.1b: Design Sequence (Domain Model → Use-Case Walkthrough → Contracts → Design Review)
 
Do this once per project after the feature list exists, and again for any
feature that adds a new entity or a new component. It is how the design gets
discovered, instead of Claude improvising it inside each SPEC.
 
1. **Domain model.** List the entities (things the system stores or reasons
   about) and the relationships between them, with multiplicity (one-to-many,
   required or optional). A short text list or a Mermaid diagram is enough.
   Name each entity by what it is, not by how it is stored.
   Where several entities share attributes or behavior, note what they
   share and whether composition or inheritance fits (see the Hierarchy
   and reuse check in the SPEC prompt).
2. **Use-case walkthrough.** Take the 2-3 most important use cases from the
   master document and walk each one step by step through the components in
   the chosen architecture: who receives the request, who decides, who
   stores. Assign each component to a layer and mark the allowed
   dependency direction (dependencies point one way; lower layers never
   call up). Write down every operation that passes between components.
3. **Contracts.** Each operation found in step 2 becomes an interface entry:
   name, inputs, outputs, preconditions, postconditions, and what failure
   looks like. These are the interfaces the SPEC will specify. Operations
   that nothing in a use case needs are not added "just in case."
4. **Design review (one page).** Show the domain model, the component
   diagram, one walkthrough, the key decisions and the open risks. Check:
   can every requirement be traced to a use case that the design handles?
   Does any entity have no owner component? Does any component do two
   unrelated jobs? You approve the design here, before any SPEC is written.
 
Ask AI Assistant #1 for this directly:
 
```
Using the master document and the feature list, produce the Design Sequence:
1. Domain model: entities and relationships with multiplicity.
2. Walk the top 2-3 use cases through the components, step by step,
   listing every operation between components.
3. For each operation: inputs, outputs, preconditions, postconditions,
   failure behavior.
4. A one-page design review: open risks, and any requirement not covered
   by a use case. Do not add entities, components or operations that no
   use case needs.
```
 
Tier: Lightweight skips this (the SPEC covers it). Structured does steps 1-3.
Formal does all four, with the design review recorded in `docs/DESIGN.md`.

### Step 2.2: Create the First Feature Spec (SPEC-001)
 
Always start with the first item in the dependency chain.
 
Prompt for AI Assistant #1:
```
Create a detailed specification for SPEC-001: Database Schema & Models.
 
Context: Personal Finance Tracker (see APP-OVERVIEW.md)
 
Include:
1. Complete database schema (all tables, columns, types)
2. Relationships between tables
3. Indexes for performance

6. Data validation rules
7. Edge cases and constraints
8. Testing requirements

   read-only endpoint with nothing worth recording.
10. Reuse/Dependency check: for any new third-party library or package
    this spec introduces, is it actively maintained (not a one-person
    project with no commits in a year)? Does its license permit the way
    you're planning to use it? Is it solving a problem substantial enough
    to justify the dependency, or would ten lines of your own code do the
    same job without adding a maintenance liability? Flag any dependency
    added for convenience where the cost (attack surface, license risk,
    abandonment risk) hasn't been weighed against the ten-line
    alternative.
11. DRY check: does this spec introduce logic, a rule, or a constant that
    already exists elsewhere in the codebase (a validation rule duplicated
    from another SPEC, a magic number that should reference a shared
    constant)? Flag it — one authoritative source, not two copies that can
    drift apart.
12. Acceptance criteria written in EARS format (see below) — no free-prose
    "should work correctly" statements.
13. For any class or module boundary this spec introduces: which
    responsibility does it own, and what would force it to change?
    (Single Responsibility check — flag anything that owns two
    unrelated reasons to change.)
```
 
For specs that define application logic rather than a schema (e.g. a
service layer, an API endpoint set, a class hierarchy), also ask AI
Assistant #1 to include:
 
```
14. Interface design: what does this module expose to the rest of the
    app, and what does it hide? For each operation, state its
    preconditions (what must be true before it's called) and
    postconditions (what's guaranteed true after it returns) — not just
    a method signature. Could a caller depend only on the interface,
    without knowing the implementation? (Dependency Inversion check —
    flag any place a high-level module reaches directly into a
    low-level implementation detail.)
15. Extension points: if a plausible future requirement arrives (a new
    payment provider, a new notification channel), does adding it mean
    extending this module or modifying it? (Open/Closed check — this
    isn't a request to pre-build extensibility you don't need yet; it's
    a request to notice where a spec design would force a rewrite later.)
16. Layer & Dependency Check (Separation of Concerns): which layer does
    this code belong to — domain/business logic, application/use-case,
    infrastructure (DB, framework, external services), or presentation?
    Does any business rule live inside a framework class (e.g. validation
    logic inside a Django model or SQLAlchemy model) where it can't be
    tested without the framework? Flag any place a domain rule depends on
    infrastructure detail — dependencies should point inward, toward the
    business logic, not the other way around.
17. Substitutability check: if this spec introduces a subclass or an
    override of existing behavior, does the override honor what callers
    of the base type already expect — or does it narrow the contract
    (accept less, promise less) in a way that breaks a caller who only
    knows the base type? (Liskov Substitution check — flag any override
    that is more restrictive than the behavior it replaces.)
18. Interface Segregation check: if this spec introduces a shared
    interface or abstract base, does every implementer actually need
    every method on it? Flag any caller that would be forced to depend on
    (or stub out) methods it never uses — that's a sign the interface
    should split into smaller, role-specific ones.
19. Law of Demeter check: does any method in this spec reach through a
    chain of objects it doesn't own to get something (`a.getB().getC()
    .doSomething()`) instead of asking an object it holds directly? Flag
    any place a method needs to know the internal structure of an object
    two or more steps removed from it — "talk to friends, not strangers."
20. Defensive Programming check: for any compulsory association (an
    object that must never exist without a related object — an Order
    that must always have a Customer, an Account that must always have
    an Owner), does the design enforce that at construction time, or
    does it rely on callers remembering to set it? For any bidirectional
    association (both sides hold a reference to each other), does the
    code that sets one side also keep the other side in sync, or can the
    two drift apart (A points to B, but B points to someone else)? Flag
    any multiplicity constraint from the design that isn't actually
    enforced in code — a comment saying "always required" is not the
    same as a constructor that rejects null.
21. Scalability check: for each endpoint, query or job in this spec, state
    the largest realistic input it must handle (from the Scale answers in
    Step 1.2) and flag any of these: a list or query with no limit or
    pagination; a query run once per item inside a loop (N+1); a call to
    an external service with no timeout, or a retry that could perform a
    write twice; a write that is not safe to repeat (double-submit,
    retried request) and has no uniqueness constraint or idempotency key;
    per-user state held in process memory instead of the database (breaks
    the moment a second process runs); input with no maximum size. Do not
    add caching, queues or extra services here — name the risk and the
    simplest fix, and mark the rest "Revisit if:".
22. Hierarchy and reuse check: if this spec introduces classes that share
    attributes or behavior, state what they have in common and where each
    shared method lives. Default to composition (an object holds another
    object and delegates to it); use inheritance only for a true "is-a"
    where every subclass honors the superclass's contract (see the
    Substitutability check) and the hierarchy stays shallow. Use an
    interface to share a contract with no state; use an abstract class
    only to share state or default behavior among closely related classes.
    Flag any subclass created just to reuse code, and any hierarchy more
    than two or three levels deep.
23. Examples table: for each operation in this spec, give 3-6 concrete
    cases as input -> expected output (normal, boundary and invalid,
    chosen with EP + Boundary Value Analysis), written as a table. These
    examples become the tests: they are copied into the implementation
    prompts, and the tests are written (and seen failing) before the code
    that makes them pass.
```

🧠 Why SOLID checks belong in the spec, not left implicit
 
AI code generators default to whatever pattern is statistically common in
their training data — which is often fine, but not automatically aligned
with your specific module boundaries. Asking the Single Responsibility
question explicitly at spec time (not after the code exists) catches a
common failure mode: a class that started with one job and accumulated a
second one because nobody drew the boundary on paper first.
 
The Layer & Dependency Check catches a related but distinct failure mode:
AI code generators default to putting business rules wherever the framework
makes it easiest, which is usually the framework's own classes — a Django
model, an SQLAlchemy model, a Flask route handler. That's fast to write and
genuinely fine for a small MVP, but it means the business rule can't be
tested without spinning up the framework, and it can't move if you ever
change frameworks. Asking "which layer does this belong to?" once, at spec
time, at least makes that coupling a visible decision instead of a default.
This is Dijkstra's Separation of Concerns applied at the module boundary,
not just a house style — the Layer check and SoC are the same discipline
under two names.
 
Liskov, Interface Segregation, and Law of Demeter round out the checks AI
generators most reliably get wrong, precisely because each failure mode
still compiles and often still passes a shallow test:
 
- **Liskov violations are invisible until a caller assumes the base
  contract.** An AI extending a class will happily narrow what an override
  accepts or promises, because nothing about "override this method" says
  it has to honor the original's contract. The bug shows up later, in
  code that was written correctly against the base type and breaks the
  moment a narrower subclass is substituted in.
- **Interface Segregation gets skipped because a single fat interface is
  faster to generate than several small ones.** The cost lands on every
  future implementer forced to stub out methods they'll never use.
- **Law of Demeter violations are an AI default, not an exception** —
  chaining through `a.b.c.d()` is often the shortest path to the value a
  generated function needs, and nothing about "make it work" flags that
  the function now silently depends on the internal shape of an object
  it doesn't own.
- **Defensive Programming gets skipped because the happy path works fine
  without it.** A constructor that accepts a null "required" reference
  compiles, runs, and passes every test that doesn't specifically try to
  break it. The gap only shows up later, as a `NullPointerException` three
  layers away from where the actual mistake was made — or worse, as
  silently corrupted data (an Account with no Owner) that nothing ever
  raises an error about. This matters most in framework-heavy OOP code
  (Laravel/Symfony-style models with real relationships, not just data
  containers), where a "required" relationship is easy to state in a
  migration or an annotation and easy to forget to actually enforce in
  the constructor.
 
All four checks above — SRP, the Layer & Dependency Check, Interface
Segregation, and Law of Demeter — are really one discipline wearing four
names: reducing coupling (how much one part depends on another's
internals) and increasing cohesion (how tightly a part's own
responsibilities belong together). Naming that umbrella once is useful
because it's the test to fall back on when a specific check feels like
it doesn't apply cleanly: "does this change make two things more
entangled, or one thing less focused?" is the question underneath all
four.
 
DRY deserves its own line in the base list, not just the extended one,
because it isn't OOP-specific — a duplicated validation rule or a repeated
magic number is exactly as much of a DRY violation in a database migration
as in a service class. Catching it at spec time is cheap; catching it
after two copies have already drifted apart is not.
 
Logging deserves the same base-list placement, for a different reason:
it's easy to treat as an implementation detail Cursor will "just add,"
and Cursor's default is either nothing or a scattered `print()` wherever
it happens to be debugging its own generated code. Naming what needs a
log entry — and at what level — at spec time means the log file can
actually answer the question you'll ask it in six months ("did this
webhook call reach the provider?"), instead of being noise that happens
to exist.
 
The Reuse/Dependency check exists because "just install a package" is
the AI default when a problem looks even slightly non-trivial — and the
cost of that default is invisible at generation time. An abandoned
one-maintainer package, a license that doesn't actually permit your use
case, or a dependency pulled in to solve something ten lines would have
handled are all costs that surface months later, not at the moment
Cursor suggests `npm install some-trendy-package`. This is the reuse
version of YAGNI: reused code isn't free just because it's someone
else's code — it's a liability you're choosing to take on, and the spec
is where that choice should be visible and deliberate, not buried in an
import statement nobody reviewed.
 
This isn't about applying SOLID, layering, or design patterns
dogmatically everywhere — a five-week solo MVP does not need
enterprise-grade abstraction layers, and over-applying Open/Closed, a
full four-layer architecture, or a GoF pattern to code that will never
actually need it is its own kind of waste (see YAGNI, Common Mistake 3
below). A pattern earns its place only when it produces a substantial,
not superficial, improvement to this specific design — reaching for
Observer or Command because the pattern is familiar, not because the
problem actually calls for it, adds classes and indirection for no real
gain. The point is narrower: ask the question once, at design time, so
that if a responsibility or layer boundary should exist, it's a
decision — not something that emerges by accident three specs later when
a "model" class has quietly grown business logic, framework code, and
presentation formatting all in one place.

🧠 Why the gate is a separate file, not a line inside the SPEC
 
A "Status: Planning" line inside SPEC-001.md is easy to overlook — the

A finished-looking document is not the same thing as an approved one.
 
Splitting the gate into its own file makes the rule enforceable, not just
advisory: **file existence does not imply approval.** If `SPEC-001.status`

document. You update the `.status` file yourself, as a deliberate act,
after actually reading the spec. That one-word edit is the whole gate.
 
---
 
**Before you make that edit — Requirements Validation, not Verification.**
 
Verification with Evidence (Step 4.7) asks "does the code match what the
spec says?" That's a different question from "does the spec say what I
actually meant?" — and the second one needs answering first, while it's
still cheap to fix.
 
Before changing `.status` to `approved`, do one cheap check: reformulate
the SPEC's core requirements back in plain language, in your own words,
and confirm they match what you actually intended — not what the document
technically says. If a stakeholder is involved, do this reformulation out
loud to them, the same way you would in a real interview (Step 1.2c). If
it's a solo project, do it against your own memory of what you meant when
you started the conversation.
 
This catches a specific failure mode: a spec can be internally consistent,
fully mapped in the Requirements Mapping table, and still not be the thing
you meant to build — because AI Assistant #1 filled a gap with a
plausible-sounding assumption you never corrected. A finished-looking
document passes every mechanical check in this workflow and can still be
wrong in this one way that none of them catch.

---
 
🧠 Why the Requirements Mapping table is not optional
 
This table is the single fastest way to catch a spec that looks complete
but isn't. Writing FR-3 and never mapping it to a design decision means
either the design silently doesn't cover it, or it's covered somewhere
nobody wrote down — both are the same problem from AI Assistant #2's
perspective: an implementation with no anchor. Filling every row forces
the check before code exists, not after AI Assistant #2 guesses.
 
---
 
🧠 Why EARS format matters
 
Five sentence shapes — WHEN (event-driven), IF (unwanted behavior), WHILE
(state-driven), WHERE (optional feature), and the plain "THE SYSTEM SHALL"
(ubiquitous) — cover nearly every requirement you'll ever write, and each
one reads like an executable contract rather than a description. "The form
should validate correctly" leaves the AI to invent what "correctly" means.
"IF the amount is <= 0, THE SYSTEM SHALL reject with 422" leaves nothing
to invent. Each EARS line maps almost directly onto a test case, which is
exactly the point: a requirement you can't turn into an assertion isn't
really a requirement yet.
 
---
 
### Choosing Test Values: Equivalence Partitioning + Boundary Value Analysis
 
EARS format fixes *how* a requirement is worded. It doesn't tell you
*which specific values* to test. "IF the amount is <= 0" needs a concrete
test suite — testing amount=1000 alone doesn't verify that boundary at all.
 
**Equivalence Partitioning (EP):** group possible inputs into buckets the
system is likely to treat the same way, then test one value from each
bucket instead of testing everything. For `amount`:
 
```
Partition 1: amount <= 0        (invalid — should reject)
Partition 2: amount > 0         (valid — should accept)
```
 
**Boundary Value Analysis (BVA):** bugs cluster at the edges of these
partitions, not their middles — an off-by-one in `<=` vs `<` is exactly
the kind of thing that only shows up at the boundary. Test the values
immediately on both sides of each partition edge, not just one value
comfortably inside it:
 
```
amount = -1    (just inside "invalid")
amount = 0     (the boundary itself — is 0 valid or not?)
amount = 1     (just inside "valid")
```
 
Ask AI Assistant #1 to derive EP+BVA test values as part of writing the
Acceptance Criteria, not as a separate afterthought:
 
```
For each EARS requirement with a numeric or range condition, identify
the equivalence partitions and list the boundary values to test for
each partition — not just one value comfortably inside it.
```
 
---
 
🧠 Why this matters beyond "more tests"
 
A test suite with one passing value per requirement proves the happy
path works. It says nothing about the boundary — which is precisely
where an AI-generated `<` vs `<=` typo, or an off-by-one in a loop
condition, actually lives. EP keeps the test count from exploding (you
don't need to test every integer, just one representative per bucket);
BVA makes sure the values you do pick are the ones most likely to catch
a real bug. This is also a credibility signal in its own right: a test
suite that visibly tests `0`, `-1`, and `1` around a `<= 0` condition
reads as deliberately designed, not just "some examples the AI came up
with."
 
---
 
🧠 What AI Assistant #1 is doing here
 
AI Assistant #1 is translating your high-level feature idea into engineering specifications — the kind a senior developer would hand to a junior developer, or a tech lead would review in a code review.
 
Notice a few things AI Assistant #1 is doing that you might not think to do yourself:
 
**Cascade rules:** When you delete a user, what happens to their data? The AI is thinking about data integrity automatically. Without explicit cascade rules, you get "orphan records" — database rows with no parent, which cause subtle bugs months later.
 
**DECIMAL not FLOAT:** Money should never be stored as a floating-point number. `0.1 + 0.2 = 0.30000000000000004` in floating-point math. The AI knows this is a classic mistake and prevents it.
 
**Indexes:** An index is like a book's table of contents — it makes lookups fast. Without `idx_users_email`, logging in requires scanning every row in the users table. With it, the database jumps directly to the right row. The AI adds indexes where queries will be frequent.
 
These aren't things you'd typically learn until you'd made the mistakes. The AI is passing on accumulated engineering knowledge.

```
  written, and seen failing, before the code that makes them pass
- Reference the original spec
```
 
---
 
🧠 What AI Assistant #1 is doing here
 
AI Assistant #1 is taking your spec and chunking it into pieces that are the right size for an AI code generator to handle reliably.
 
This is important: AI code generators (including AI Assistant #2) work best on focused, bounded tasks. "Build me the entire app" produces mediocre results. "Create the SQLAlchemy User model with these exact fields and these validation methods" produces excellent results.
 
AI Assistant #1 is essentially writing the briefs that the code-generating AI will follow. It's optimizing the prompts for the tool that will actually write the code — a kind of meta-prompting.
 
Every prompt AI Assistant #1 generates must include an IMPLEMENTER RULES block (see the example prompt above). This is not optional boilerplate — it locks in six behaviours that AI code generators get wrong by default:
 
- **Full file output:** Cursor often returns partial code with `# ... rest unchanged`. This makes diffs unclear and merges error-prone. The rule forces complete output every time.
- **Functional style:** AI-generated OOP often hides state and edge cases inside classes. Pure functions are easier to test, debug, and reason about. Default to functional; use classes only when the spec or framework requires them.
- **`for` over `while` for constrained generation:** A `while` loop generating values under a constraint will hang forever if the constraint can't be satisfied (e.g., generating a wrong-answer distractor when only one answer exists). A `for` loop with a fixed limit guarantees an exit. This was a real production bug.
- **No invented context:** Even with `@workspace` access, Cursor will sometimes hallucinate a function or variable it hasn't actually seen, especially in a large codebase. The rule forces it to flag missing context instead of generating silently broken code.
- **No extra features:** Cursor will "helpfully" add logging, caching, or error handling you didn't ask for. Each addition is untested scope creep. The rule keeps the diff minimal and reviewable.
- **Explicit join types:** An unstated inner join silently drops rows; an unstated left join silently duplicates them if the join key isn't unique. Cursor will pick a join type without telling you which one or why — forcing this into the open prevents a whole class of silent data bugs.
- **Code documentation standard:** SPEC.md and DECISIONS.md document *why the project made a choice*. They do not help a developer who opens `models.py` cold and needs to know what one function expects and returns right now. Without an explicit rule, Cursor's docstring habits are inconsistent — sometimes thorough, sometimes a one-line stub, sometimes nothing. The rule makes documentation land where a future reader (including future you) will actually look first: in the code itself.

### Step 4.4b: Git & GitHub Hygiene (Set Up Once, Check Every Commit)
 
Commit cadence is only half of professional git discipline. The rest keeps
secrets and junk out of history, keeps each commit useful for debugging, and
makes every release reproducible.
 
1. **`.gitignore` before the first commit.** Ignore at least: `.env` and any
   file holding secrets, dependency folders (`node_modules/`, `venv/`,
   `.venv/`, `vendor/` if your ecosystem restores it), build output
   (`dist/`, `build/`, `__pycache__/`, `.next/`), coverage reports
   (`htmlcov/`, `coverage/`), local databases, and editor folders. Commit a
   `.env.example` with variable names and no values.
2. **Commit the lockfile.** `package-lock.json`, `poetry.lock`/`uv.lock`,
   `composer.lock` — whichever your ecosystem produces. It records the exact
   resolved versions (including transitive dependencies), so the dependency
   scan in the Quality Gate checks what actually runs, and a build next
   month matches a build today.
3. **Secrets never enter history.** Run a secret scan (e.g. `gitleaks`)
   before the first push and as part of the pre-push check. If a secret is
   committed, deleting it in a new commit is NOT enough — it stays in
   history. Revoke and rotate the credential first, then clean the history
   if the repository was ever shared.
4. **One logical change per commit.** Do not mix a feature with a refactor,
   or a fix with unrelated cleanup. Use the existing message convention
   (`feat(scope): ... [SPEC-001, PROMPT-001]`, `fix:`, `refactor:`,
   `docs:`, `test:`). Small, self-contained commits keep `git bisect`
   (find which commit broke it) and `git revert` (undo exactly one change)
   usable. A bug fix is committed on its own, together with its regression
   test.
5. **Branch per SPEC, merge through a Pull Request (Structured recommended,
   Formal required).** Work on `spec-001-<name>`; open a PR whose
   description contains the SPEC link, the Requirements Mapping rows it
   satisfies and the Verification-with-Evidence block; merge only after the
   Automated Quality Score Gate output is attached. On a solo project,
   review your own PR diff line by line before merging — the diff view
   catches what the editor hides. Lightweight projects may commit directly
   to `main`.
6. **Tag every release.** `git tag -a v0.1.0 -m "MVP: SPEC-001..003"` then
   `git push --tags`. A tag lets you reproduce, roll back to, or bisect from
   exactly what shipped.
7. **Never rewrite shared history.** No force-push to `main`. Use
   `git revert` to undo something already pushed.
8. **CI mirrors the Quality Score Gate (Structured recommended, Formal
   required).** Configure the repository's CI (GitHub Actions if you host
   on GitHub; any provider works) to run the same commands as the
   Automated Quality Score Gate on every push and PR, and block merging
   when they fail. Rules for the CI configuration itself:
   - Run the project's own commands (the ones in the Quality Gate), not a
     different set — local and CI results must agree.
   - Pin third-party actions/images to a specific version or commit SHA,
     never a floating tag.
   - Give the workflow the least permissions it needs (read-only by
     default), and keep secrets out of logs and out of runs triggered from
     forks.
   - Treat the CI file like application code: read every line of an
     AI-generated workflow before committing it, since it executes with
     access to your repository.
   - The CI result is evidence: attach the run link or output to the PR's
     Verification-with-Evidence block.
   Lightweight projects may rely on the local gate.

### Step 4.7: Verification with Evidence
 
When you or Cursor mark a task or prompt "done," the claim needs a receipt,
not a summary. Use this fixed format for every completion claim:
 
```
Claim:     [what you're asserting is true]
Command:   [the exact command that proves it]
Exit code: [0, or the actual number]
Summary:   [what the command's output showed]
Verdict:   PASS | FAIL
```
 
Example:
```
Claim:     Amount validation rejects zero and negative values
Command:   pytest tests/test_transactions.py -k "test_amount_validation" -v
Exit code: 0
Summary:   3 tests, 3 passed
Verdict:   PASS
```
 
Two rules that keep this honest:
 
1. **No command available? Say so, don't skip it.** "Verified manually in
   the browser — no automated test exists for this yet" is a legitimate
   verdict. "It works" with no command behind it is not.
2. **No completion claim survives on stale evidence.** If you changed the
   code after the last test run, "I ran it earlier" doesn't count — rerun
   it. The exit code has to be from *this* version of the file.
 
---
 
🧠 Why the format matters more than it looks
 
This closes the most common hole in AI-assisted execution: Cursor declaring
a task done based on what it *believes* the code does, not what it verified.
"Should work now" and "exit code 0 on this exact command" are different
claims — only one of them is checkable. The format forces the difference
into the open every time, instead of only when something breaks and you go
looking for what was actually tested.

## STAGE 5: SAFETY LAYER & ERROR HANDLING (The 80/20 Rule)
 
This stage takes 20% of the time and prevents 80% of real-world problems. Three simple habits.
 
---
 
### Step 5.1: AI Security Review ("Hacker Mode")
 
Before running any AI-generated code, paste it into AI Assistant #1 and write:
 
  "Find 3 vulnerabilities or problems in this code. For each one explain:
  what it is, why it's dangerous or breaks things, and how to fix it
  with one targeted change."
 
Then ask Cursor to apply each fix as a separate, small prompt.
 
---
 
🧠 Why AI is good at this role
 
AI Assistant #1 has been trained on millions of codebases — including the ones that had breaches and the post-mortems written afterwards. It recognizes vulnerability patterns instantly:
 
- SECRET_KEY = "hardcoded-value" → if this gets pushed to a public GitHub repo, anyone can forge session cookies and log in as any user
- sql = f"SELECT * FROM users WHERE id = {user_id}" → SQL injection. If someone passes `1 OR 1=1` as user_id, they get every record in the table
- except: pass → the error is silently swallowed. Your app will fail mysteriously and you'll have no log to debug from
 
Authentication and authorization are different questions, and AI generators
routinely answer only the first. Authentication establishes *who* is making
a request. Authorization decides whether *that identity* may perform *this
specific action on this specific resource*. A route that checks "is this
user logged in?" and stops there is vulnerable the moment someone changes
`/orders/381` to `/orders/382` in the URL — the request is authenticated,
but nobody checked that this user owns order 382. This is broken access
control, and it's consistently the most common real-world vulnerability
class precisely because the happy path (the owner viewing their own
record) tests fine and never exercises the missing check.
 
The key habit: after AI Assistant #1 explains each problem, ask AI Assistant #1 to explain why the fix works — not just what to change. This is how you build permanent pattern recognition rather than just fixing one file.
 
Example conversation:
 
  You:  "Find 3 vulnerabilities in this code: [paste code]"
 
  AI:   "1. SQL injection on line 12. You're interpolating user_id
        directly into the SQL string. An attacker who controls that
        value can inject arbitrary SQL. Fix: use a parameterized query:
        db.execute('SELECT * FROM users WHERE id = ?', (user_id,))
        The ? is a placeholder — the database driver handles escaping,
        which prevents injection regardless of what the input contains."
 
  You:  "Got it. Now give me the Cursor prompt to apply just that fix."
 
---
 
Hacker Mode checklist:
```
□ Hardcoded secrets? (passwords, API keys, SECRET_KEY)
□ SQL queries built with f-strings or string concatenation?
□ bare except: pass blocks with no logging?
□ File paths taken from user input without validation?
□ User-supplied data used directly without sanitization?
□ Authorization checked per-resource, not just "is logged in"? A route
  that checks the user is authenticated but not that this user owns
  this specific record (an order, a document, another user's data) is
  broken access control — the single most common real-world
  vulnerability class, and the one AI generators miss most often
  because "is logged in" is the easier question to answer.
□ Does every error/failure path deny by default? If a permission check
  throws, times out, or hits an unexpected case, does the code deny the
  action — or does an exception skip the check and fall through to
  allowing it?
□ Untrusted text rendered as raw HTML instead of through a text-escaping
  API? (cross-site scripting) — check any place user-supplied content
  (a name, a comment, an event title) gets displayed back in a UI.
```
 
If none found, ask again with: "Pay special attention to user input
handling, configuration, and whether authorization is checked per
resource, not just per login."
 
One rule applies to you, not just the generated code: never paste a real
secret, API key, password, or a customer's actual data into a prompt to
AI Assistant #1 or #2. Use a placeholder ("YOUR_API_KEY_HERE") when
showing an example, and remember a tool may see more context than what
you explicitly typed — connected files, terminal output, or an open tab —
so check what a tool can access before working with anything sensitive.
 
---
 
### Math Verification Gate
 
Any calculation with real consequences — a budget total, an interest rate,
a discount formula, a scoring algorithm, a distractor generator, a tax
calculation — does NOT count as verified just because AI Assistant #1 or
Cursor says it looks correct. The AI that wrote the formula is the worst-
positioned party to catch its own error: if it made a wrong assumption,
that same assumption is baked into its own check.
 
Before marking any SPEC with a non-trivial calculation as complete, verify
it through at least one of these, independent of the reasoning that produced it:
 
```
1. Independent LLM pass — different model, not just a fresh chat
   Take the formula and a worked example — no explanation of how you got
   there — to a DIFFERENT model/vendor (e.g. if Claude proposed the formula,
   check with ChatGPT or Gemini). A fresh chat with the SAME model shares
   the same architecture and training blind spots — it often reproduces
   the identical error with identical confidence.
 
2. Hand-worked example with a known answer
   Compute the result by hand (or with a calculator) for one concrete
   input, then assert the code produces that exact value in a test.
   Do not accept "the code ran" as verification.
 
3. Property-based sanity check
   For formulas with a known invariant (e.g. "total spent should never
   exceed sum of transactions", "discount should never make price negative"),
   write an assertion that checks the invariant holds, not just that the
   function returns a number.
```
 
This applies to: budget/balance calculations, any pricing or discount logic,
scoring or ranking algorithms, and any formula in a distractor/data generator
(same discipline as the for-loop rule — don't trust generated math, verify it).
 
Acceptance Check requirement: for any SPEC step involving a non-trivial
calculation, the test suite must include at least one hand-verified value,
not just a "does it run" test.
 
---
 
### Layer Boundary Verification (applies whenever Step 2.2's Layer & Dependency
Check was used)
 
The Layer & Dependency Check in Step 2.2 catches design-time intent — but
intent stated in a SPEC doesn't guarantee the generated code actually
respects it. Cursor will often draft the interface correctly and then, a
few files later, quietly import a database model directly into a domain
function because it was the fastest path to "make it work."
 
Before marking a SPEC complete where a layer boundary was named, verify it
didn't get silently violated during implementation:
 
```
□ Open the file(s) that were supposed to be domain/business logic —
  do any of them import a framework class (Django/SQLAlchemy model,
  Flask request object) directly?
□ Can the domain logic be called in a plain Python REPL, without
  starting the framework or hitting a database?
□ Ask AI Assistant #1: "Here's the SPEC's layer boundary and the
  generated files — did the implementation cross it anywhere?"
```
 
This is a quick post-implementation grep, not a new stage — but skipping it
means the Layer & Dependency Check was only ever a paper exercise.
 
---
 
### Performance Verification (applies when the SPEC or master doc states a
### performance or volume requirement)
 
A stated requirement such as "page load under 2 seconds" or "support 1,000
transactions per user" is a claim, and claims need evidence like any other.
Without it, the first load test is production.
 
1. Seed the test database with the realistic volume from the master doc's
   Scale section (not three rows).
2. Measure the specific operation (a timed request, a query with
   `EXPLAIN`, a profiler run) — with a command you can re-run.
3. Report it in the same Claim / Command / Exit code / Verdict format as
   any other evidence, including the measured number next to the target.
4. Measure before optimizing. If the target is missed, find the actual
   bottleneck with the measurement; do not guess at caching or rewrites.
   Fix the one bottleneck found, then measure again.
5. If the requirement is met with room to spare, stop — do not optimize
   past the stated target.
 
---
 
### Automated Quality Score Gate
 
Every check so far in this workflow is either you or an AI reading code and
forming a judgment. This one is different on purpose: it runs real,
external, deterministic tools and reports a number — not an opinion from
the same kind of system that wrote the code.
 
This matters for a specific reason: if your goal is code that other
engineers (or a hiring client, or a code reviewer skeptical of AI-written
work) will trust, "Claude reviewed it and it looks clean" carries no
weight. A `ruff` exit code, a `radon` complexity grade, a `bandit` report
with zero findings — those are checkable by anyone, independent of who or
what wrote the code. That's the actual argument for AI-assisted code being
production-grade: not that the AI says so, but that the same tools you'd
run against human-written code say so.
 
Run these before marking any Structured or Formal SPEC complete:
 
```
# Python
ruff check src/                    # linting — target: 0 errors
mypy src/ --strict                 # type checking — target: 0 errors
radon cc src/ -a -nb               # cyclomatic complexity — target: A/B per function
radon mi src/                      # maintainability index — target: A rank
bandit -r src/                     # security — target: 0 high/medium findings
pytest --cov=src --cov-report=term # coverage — target: 80%+ on changed lines
 
# JavaScript/TypeScript
eslint src/ --max-warnings=0       # linting — target: 0 errors, 0 warnings
tsc --noEmit --strict              # type checking — target: 0 errors
npx eslint src/ --rule 'complexity: ["error", 10]'  # complexity — target: pass
npm audit --audit-level=moderate   # dependency security — target: 0 findings
jest --coverage                    # coverage — target: 80%+ on changed lines
```
 
Report the result using the Verification with Evidence format from Step
4.7 — one Claim/Command/Exit code/Verdict block per tool, not a summary
of "linting passed."
 
If a tool fails: fix the code, don't lower the threshold to make the tool
pass. A `# noqa` or a suppressed warning added to silence the tool is the
same failure mode as lowering an assertion threshold to make a test pass
(see Math Verification Gate) — it hides the finding instead of resolving it.
 
**When the fix is structural — `radon` flags a function's cyclomatic
complexity or maintainability grade — that fix is a refactoring, and
refactoring has its own discipline.** Refactoring is not rewriting: the
external behavior must not change, and it needs to happen in small,
reversible steps, not a full rewrite of the flagged function from
scratch. Ask Cursor specifically for that:
 
```
This function is flagged for [complexity/maintainability]. Refactor it
using small, standard refactorings (extract method, consolidate
duplicate conditionals, replace nested conditionals with guard clauses)
— do not rewrite it from scratch. External behavior must not change.
After each small step, I'll rerun the existing tests before the next one.
```
 
Run the full existing test suite after the refactoring — not just the
Quality Gate — and treat any change in behavior as a regression, not an
improvement. If there's no existing test covering the function being
refactored, write one *before* the refactoring starts; refactoring
without a test watching behavior is indistinguishable from rewriting.
 
---
 
🧠 Why this gate exists, and why it's not redundant with Hacker Mode
 
Hacker Mode is AI Assistant #1 reading code and reasoning about
vulnerabilities. It's good at spotting patterns but it's still a language
model's judgment, and it's the same category of system that might have
written the vulnerable code in the first place. `bandit` doesn't reason —
it pattern-matches against a fixed, published ruleset that doesn't share
any blind spots with the model that generated the code.
 
The five categories above (lint/reliability, types, complexity,
maintainability, security, coverage) are not arbitrary — they're the same
categories that tools like SonarQube, CodeClimate, and Codacy score
automatically when someone runs your repo through them. Passing this gate
before you ship means you already know what those tools will say, instead
of finding out when a client or a reviewer runs one and you're explaining
the score after the fact.
 
This is also where the Implementer Rules' style guide requirement (Rule
9) and the linter meet: `ruff` and `eslint` are the actual enforcement
mechanism for PEP 8 or whatever guide steering/conventions.md names.
Stating the guide up front reduces how many violations the generator
produces in the first place; the linter is the backstop that catches what
slips through, not the only line of defense.
 
---
 
### Step 5.2: Delegating Terminal Errors
 
Rule: When anything breaks in the terminal — copy the full error log and paste it into Cursor Chat (Ctrl+L). Do not try to decode the traceback yourself.
 
Format your request:
 
  "Here is the full error log. Explain: 1) what broke, 2) why it happened,
  3) how to fix it. Don't just give me code — explain the cause."
 
---
 
🧠 Errors as learning moments
 
Python tracebacks read bottom-up. The last line is the actual error; the lines above show the call stack — how the program got there. This is counterintuitive until you've seen it dozens of times.
 
Before accepting any fix, ask: "Why did this break? Is it a problem with my code or with the environment?"
 
Common error categories and what they mean:
 
```
ModuleNotFoundError  → Package not installed, or virtual environment not activated.
                       Fix: pip install <package> or activate venv.
 
IntegrityError       → Database constraint violated — duplicate value in a
                       UNIQUE column, or NULL in a NOT NULL column.
                       Fix: check your data before inserting, or check your schema.
 
TypeError            → A function received the wrong type of data.
                       "expected str, got int" means somewhere a string is
                       being passed where an integer is expected (or vice versa).
 
KeyError             → Accessing a dictionary key that doesn't exist.
                       Fix: use dict.get('key') instead of dict['key'], or
                       check that the key exists first.
 
AttributeError       → Calling a method or accessing a property that doesn't exist
                       on that object. Often means you have the wrong variable type.
```
 
Practical habit: Keep a personal errors file at docs/MY-ERRORS.md. Each time you hit a new error type, write one sentence about what it meant in your context. Within a month, you'll recognize most errors on sight.
 
---
 
### Hypothesis Discipline (Before Accepting Any Fix)
 
Cursor's explanation of what broke is a hypothesis, not a fact — the same
caution as Math Verification Gate and the Automated Quality Score Gate,
applied to debugging. Cursor is unreliable at diagnosing a defect in code
it cannot actually run, and it will produce a confident, fluent,
*incorrect* explanation with the same tone as a correct one. Nothing about
how it's phrased tells you which you got.
 
Before applying a fix, make Cursor's explanation falsifiable:
 
```
1. State the hypothesis in one sentence: "X is wrong because Y."
   Not "something's wrong with the validation" — "the amount field is
   receiving a string because the form doesn't cast it before submit."
2. Ask: what would I observe if this is true? What would I observe if
   it's false?
3. Check the specific thing the hypothesis predicts — a print statement,
   a debugger watch, an assertion — before applying the fix, not after.
4. Only then apply the fix.
```
 
If Cursor can't state a falsifiable hypothesis — only "try this and see if
it works" — that's shotgun debugging with extra steps, and it means you
don't yet understand the cause well enough to have earned a fix. Ask for
the hypothesis again, or investigate it yourself, before changing code.
 
---
 
🧠 Why this matters more than it sounds
 
The failure mode this catches: Cursor patches whatever line the traceback
points to, the error message disappears, and you move on — without either
of you actually knowing why the original code was wrong. The fix might be
correct. It might also have masked the real defect one frame up, or fixed
the symptom while the cause is still there waiting to resurface in a
different form. A stated, checked hypothesis is what separates "the error
went away" from "I know why the error happened."
 
---
 
### Regression Test Requirement
 
A fix isn't done until you have a test that fails on the old code and
passes on the new code. If you don't have one, write it before you
consider the bug closed — it's the cheapest proof that you fixed the
cause and not just this one occurrence of the symptom.
 
This folds into Step 4.7's Verification with Evidence: the Command in
your Claim/Command/Exit code/Verdict block for a bug fix should be that
regression test specifically, not just "the test suite passes." A test
suite that passes because the new test happens to pass alongside
unrelated ones doesn't tell you the fix addressed the reported failure.
 
---
 
### Step 5.3: Change Discipline (Document First, Code Second)
 
Rule: Any new idea or change in requirements gets written into APP-OVERVIEW.md or the relevant SPEC-XXX.md first. Only then do you trigger code generation in Cursor.
 
What this looks like in practice:
 
Bad (how most beginners work):
  "Oh, it would be great to add an export button! Cursor, add an export feature."
  → Code is generated. It breaks three other components. You don't know why.
 
Good (SDD discipline):
  1. Open SPEC-003.md
  2. Add a section:
     "## New Idea: CSV Export
      Reason: users need to analyze data in spreadsheets.
      Impact: new button in transaction list UI, new /export endpoint,
      depends on SPEC-003 transaction query logic."
  3. git commit -m "docs: Add CSV export idea to SPEC-003"
  4. Open Cursor Composer (Ctrl+I):
     "@docs/specs/SPEC-003.md — add the CSV export feature described
     in the new section at the bottom of the file"
 
---
 
🧠 Why this matters more than it seems
 
Without documented change history, in two weeks you won't remember why you added that endpoint. In a month, you can't explain it to a client. In three months, you can't explain it to yourself.
 
SDD turns the chaos of vibe-coding into an auditable decision log. Every git commit that changes a document is a record: "I decided X for reason Y at time Z."
 
This is the difference between a junior developer and a senior developer — not the speed at which they write code, but their ability to explain why the code is the way it is.
 
Stage 5 checklist:
```
□ Code reviewed for 3 vulnerabilities before running?
□ All terminal errors delegated to AI with full log?
□ New ideas documented before code generation?
□ Understood the cause of at least one error (not just applied the fix)?
□ Every non-trivial calculation passed the Math Verification Gate
  (independent LLM check against a DIFFERENT model, hand-worked value,
  or invariant assertion — not a same-model self-check)?
□ If a layer boundary was named in SPEC: confirmed it wasn't crossed
  during implementation (not just stated at design time)?
□ Every public function/class has a docstring and type hints — checked by
  opening the file, not by trusting the AI said it added them?
□ Every completion claim has Claim/Command/Exit code/Verdict — not just
  "it works"?
□ SPEC-NNN.status actually says `approved` before implementation started —
  checked the file, not assumed from the document looking finished?
□ Automated Quality Score Gate run with real tool output — not an AI's
  opinion that the code "looks clean"?
□ Every applied fix had a stated, checked hypothesis first — not just
  "Cursor's explanation sounded right"?
□ Every bug fix has a regression test that fails on the old code and
  passes on the new code?
```

## STAGE 7: Replanning (Between Features)
 
This stage comes from Andrew Ng's SDD course and is one of the most
valuable habits in the entire workflow. Most developers skip it. Don't.
 
---
 
### Step 7.1: Review What You Just Built
 
Before starting the next feature, take 10 minutes to ask AI Assistant #1:
 
  "I just completed SPEC-001 [paste the Implementation Status section].
  Based on what we built and what we learned, should we update anything
  in APP-OVERVIEW.md or FEATURE-PLAN.md before we continue?"
 
This is not bureaucracy. This is the moment where accumulated small
discoveries get recorded before they're forgotten.
 
---
 
🧠 What AI Assistant #1 is doing here
 
It's acting as a retrospective facilitator — a role that Agile teams formalize
into a full meeting. You're getting the same value in 10 minutes of conversation.
 
Every feature you build teaches you something you didn't know when you wrote
the spec. Maybe the database schema needs an extra column you didn't anticipate.
Maybe SPEC-004 now depends on something you built in SPEC-001 in a way that
wasn't in the original plan. Maybe you realized the tech stack choice has a
limitation that affects three future features.
 
Without Replanning, those discoveries stay in your head and leak out as
inconsistencies later. With Replanning, they become part of the official record.
 
---
 
### Step 7.2: Update the Constitution (APP-OVERVIEW.md)
 
If anything fundamental changed — tech stack decision, a constraint you
discovered, a scope change the client requested — update APP-OVERVIEW.md now.
 
Prompt for AI Assistant #1:
  "Based on what we learned in SPEC-001, here are the changes I want
  to make to APP-OVERVIEW.md: [describe changes].
  Draft the updated sections for me."
 
Commit:
```bash
git add docs/APP-OVERVIEW.md
git commit -m "docs: Replan after SPEC-001 — update [what changed and why]"
git push
```
 
---
 
🧠 Why the commit message format matters here
 
Notice the message: "Replan after SPEC-001 — update [what changed and why]"
This is different from the regular "docs: Update APP-OVERVIEW with SPEC-001 completion."
 
The Replanning commit is a *decision record*, not a status update. Six months
from now, reading your git log, "Replan after SPEC-001 — switched from SQLite
to PostgreSQL after discovering concurrent write limitations" tells a story.
"docs: Update APP-OVERVIEW" tells nothing.
 
---
 
### Step 7.3: Update the Roadmap (FEATURE-PLAN.md)
 
Check your feature list. Ask:
- Did SPEC-001 reveal any new features we need to add?
- Did anything turn out simpler than expected? (remove or merge specs)
- Did the order of dependencies change?
- Are any upcoming specs now more complex than estimated?
 
Update FEATURE-PLAN.md accordingly and commit.
 
---
 
### Step 7.4: Improve the Process Itself
 
This is the meta-level habit — and the one that compounds over time.
 
Ask AI Assistant #1:
  "Looking at how SPEC-001 went: what would have made the spec clearer?
  What would have made the Cursor prompts more effective?
  Suggest one concrete improvement to our SDD template."
 
If the suggestion is good, update your spec template or prompt template.
 
---
 
🧠 Why this makes every project better than the last
 
Most developers repeat the same mistakes across projects because they never
stop to codify what they learned. The Replanning phase turns each completed
feature into a small improvement to your process.
 
After five projects with Replanning, your specs will be sharper, your prompts
will produce better first-try code, and your APP-OVERVIEW template will reflect
real-world patterns rather than theoretical ones. This is the compounding
advantage that separates developers who get faster over time from those who
plateau.
 
---
 
Replanning checklist:
```
□ AI Assistant #1 reviewed completed SPEC for lessons learned?
□ APP-OVERVIEW.md updated if anything fundamental changed?
□ FEATURE-PLAN.md updated — new features, revised estimates, reordered deps?
□ One process improvement identified and applied to templates?
□ All changes committed with descriptive "Replan after SPEC-N" messages?
□ Check the "Revisit if:" trigger in the Architecture Decision section —
  has that condition been met? (e.g. usage grew, a second developer joined)
□ Is any entry in decisions.md now wrong? Mark it Superseded and add a
  new entry; never edit or delete the old one.
```

## Common Mistakes
 
1. Skipping the Application Overview
   Problem:  Starting directly with SPEC-001. The big picture is unclear.
   Fix:      ALWAYS start with APP-OVERVIEW.md.
 
2. Letting the AI pick the architecture by default
   Problem:  AI Assistant #1 drafts APP-OVERVIEW.md with one architecture
             already baked in. You approve it by not objecting, not by
             deciding — and six months later nobody remembers why the
             app is a monolith instead of modular, or why SQLite instead
             of Postgres.
   Fix:      Run Step 1.2b before the document is written: ask for 2-3
             options with trade-offs, choose explicitly, write down why.
 
3. Applying SOLID/layering dogmatically on a small project
   Problem:  The spec asks for Dependency Inversion, Open/Closed, a full
             domain/application/infrastructure split, etc. everywhere, and
             a five-week solo MVP ends up with interface layers, abstraction
             points, and folder structures for a scale it will never reach.
             This is YAGNI violated in the opposite direction.
   Fix:      The SOLID and layering checks in Step 2.2 are questions to ask,
             not rules to always apply. "This class does two unrelated
             things" or "this validation rule can't be tested without
             Django" is worth fixing. "This could theoretically be more
             extensible" or "this doesn't have a formal domain layer" is
             not, unless a concrete near-term requirement demands it.
 
4. Specifications that are too large
   Problem:  A 50-page spec is impossible to implement in one pass.
   Fix:      Split large features into sub-specs (SPEC-001a, SPEC-001b, ...)
 
5. Prompts that are too vague
   Problem:  Cursor doesn't know what exactly to build.
   Fix:      AI assistant should create very specific prompts with concrete examples.
 
6. Not updating documentation
   Problem:  Documents become stale. No one knows what's done.
   Fix:      Update SPEC and APP-OVERVIEW after every completed feature.
 
7. Accepting AI code without reading it
   Problem:  You accumulate code you don't understand. Debugging becomes impossible.
   Fix:      Read every generated file. Ask AI Assistant #1 to explain anything unclear.
             Ask AI Assistant #1: "What does this decorator do and why is it needed here?"
 
8. Accepting partial output from Cursor
   Problem:  Cursor returns a snippet with `# ... rest unchanged`. You apply it
             incorrectly, overwrite the wrong section, or miss a conflict. File
             is broken in a way that's hard to trace.
   Fix:      The IMPLEMENTER RULES block in every prompt requires the full file.
             If Cursor returns partial output anyway, send back:
             "Return the complete file. No ellipsis, no truncation."
 
9. Using `while` loops for constrained value generation
   Problem:  A `while` loop that picks "a random value satisfying condition X"
             will hang forever if the constraint can't be satisfied — for example,
             picking a wrong-answer distractor when only one possible value exists.
             The app freezes silently with no error message.
   Fix:      The IMPLEMENTER RULES require `for` loops with a fixed iteration
             limit for all constrained generation. Always include a fallback
             return value for when the loop exhausts its iterations.
 
10. Writing OOP where functions would do
    Problem:  Cursor wraps simple logic in classes with `__init__`, `self`, and
              internal state. This looks professional but hides bugs — state
              mutates in ways you can't see, and AI-generated OOP is harder
              to test and debug than plain functions.
    Fix:      The IMPLEMENTER RULES default to functional style. If Cursor
              generates classes for stateless logic, add "No classes. Pure
              functions only." to that prompt explicitly.
 
11. Trusting a calculation because the same AI that wrote it also checked it
    Problem:  If Cursor made a wrong assumption writing a formula (e.g. a
              budget total, a discount calculation), the same wrong assumption
              is present when it "verifies" its own work — the check and the
              error share a blind spot.
    Fix:      Run the Math Verification Gate: independent check against a
              DIFFERENT model, a hand-worked example with a known value, or
              an invariant assertion. "The AI said it's right" is never
              sufficient sign-off for a calculation with real consequences.
 
12. Letting the AI choose a SQL join type implicitly
    Problem:  Cursor picks inner join when you needed left join (silently
              dropping rows), or the reverse (silently duplicating rows if
              the join key isn't unique). Neither failure raises an error —
              the query just returns wrong data.
    Fix:      The IMPLEMENTER RULES require the join type and key uniqueness
              to be stated explicitly in the prompt, never left for the AI
              to infer.
 
13. Confusing process documentation with code documentation
    Problem:  APP-OVERVIEW.md and SPEC-001.md are thorough, but `models.py`
              has no docstrings and no type hints. Six months later, a
              colleague (or you) opens the file and has to go find and reread
              the spec just to understand what one function returns.
    Fix:      The Code Documentation Standard rule requires docstrings, type
              hints, and "why not what" comments in every generated file.
              Verify by opening the file and reading it cold — not by
              trusting the AI's summary that it "added documentation."
 
14. Treating a finished-looking SPEC as an approved one
    Problem:  SPEC-001.md reads complete — sections filled, schema drawn,
              acceptance criteria written — so you (or Cursor) start
              implementing off it. Nobody actually reviewed it and said yes.
    Fix:      The SPEC-NNN.status file is the only thing that authorizes
              implementation. A well-formatted document is not the same
              claim as a file that says `approved`. Check the `.status`
              file, not how finished the SPEC reads.
 
15. Trusting Hacker Mode's opinion instead of running real tools
    Problem:  AI Assistant #1 reviews the code, says it looks secure and
              well-structured, and that gets treated as equivalent to a
              quality gate. It isn't — it's the same category of system
              that may have written the flaw, forming a judgment about its
              own output.
    Fix:      Run the Automated Quality Score Gate. `ruff`, `mypy`,
              `bandit`, `radon` don't reason about your code — they
              pattern-match against fixed, external rulesets. That
              independence from the model is the entire point. Hacker Mode
              and the Quality Score Gate are complementary, not redundant:
              one catches things a static tool can't see, the other catches
              things a language model's judgment can't be trusted to see.
 
16. Approving a SPEC that's internally consistent but not what you meant
    Problem:  Every mechanical check passes — Requirements Mapping is
              complete, EARS criteria are well-formed, the schema is
              sound — and the SPEC still describes the wrong thing,
              because AI Assistant #1 filled an unstated gap with a
              plausible assumption nobody corrected.
    Fix:      Requirements Validation (Step 2.3) before `.status` flips
              to `approved`: restate the core requirements in your own
              words and confirm they match intent. This is a different
              check from Verification with Evidence — one asks "does the
              code match the spec," the other asks "does the spec match
              what I meant." Skipping the second one is how a
              well-documented project ships the wrong feature.
 
17. Running parallel AI sessions to catch up on a deadline
    Problem:  Behind schedule, the instinct is to open three Cursor
              sessions on three features at once, expecting three times
              the output. Brooks' Law's core insight still applies even
              with AI instead of hired engineers: the constraint was never
              typing speed. Reviewing three diffs, keeping three SPECs
              consistent with each other, and catching where two sessions
              made incompatible assumptions costs more attention than one
              session ever did — and that cost lands hardest exactly when
              you're most rushed and least likely to catch it.
    Fix:      A rushed deadline is a reason to narrow scope (cut a
              Non-Goal, ship less) or extend the timeline, not a reason to
              parallelize coordination you don't have slack to do well.
              If you do run parallel sessions, keep them on genuinely
              independent SPECs with no shared files — the moment two
              sessions touch the same module, the coordination overhead
              exceeds what either session saved you.
 
18. Accepting a fix because the error message disappeared
    Problem:  Cursor patches the line the traceback points to, you rerun,
              the error is gone, and you move on — without either of you
              knowing why the original code was wrong. The fix might be
              correct. It might also have masked the real defect one
              frame up, which resurfaces later in a different form that's
              harder to connect back to this one.
    Fix:      Hypothesis Discipline (Step 5.2): before applying a fix,
              Cursor states a falsifiable hypothesis — what you'd observe
              if it's right, what you'd observe if it's wrong — and you
              check that specific thing before applying the change, not
              after. "The error went away" is not the same claim as "I
              know why the error happened." Pair this with a regression
              test that fails on the old code and passes on the new code;
              a fix with no such test hasn't proven it addressed the
              reported failure, only that today's specific run stopped
              complaining.
 
19. Stating a required relationship in the design but never enforcing it in code
    Problem:  The SPEC says "every Order must have a Customer" or "every
              Account must have an Owner," the schema even has a NOT NULL
              constraint — but the constructor happily accepts a null
              reference at the application layer, and nothing stops a
              caller from creating the invalid object in memory before it
              ever reaches the database. This surfaces later as a
              NullPointerException or silently corrupted data, far from
              where the actual mistake was made. Especially common in
              framework-heavy OOP code (Laravel/Symfony-style models with
              real relationships) where the relationship is declared in
              an annotation or migration and assumed to be "handled."
    Fix:      Run the Defensive Programming check (Step 2.2) on any
              compulsory or bidirectional association. A "required"
              relationship needs a constructor or setter that actively
              rejects null, not just a schema constraint that only fires
              on the eventual database write.
 
20. Treating a flagged refactoring as an invitation to rewrite
    Problem:  `radon` flags a function's complexity, you ask Cursor to
              "clean this up," and it comes back with the function
              rewritten from scratch — different structure, possibly
              different edge-case behavior, no way to confirm nothing
              changed except by re-reading the whole thing. Refactoring
              and rewriting solve different problems; asking for one and
              getting the other means you can no longer trust that
              behavior was preserved.
    Fix:      Explicitly ask for small, named refactorings (extract
              method, guard clauses, consolidate duplicate conditionals)
              — not "clean this up" — and require a passing regression
              test both before and after. If there's no test on the
              function yet, write one first; refactoring without a test
              watching behavior is a rewrite wearing a smaller name.
 
21. Accepting a suggested dependency without weighing its cost
    Problem:  Cursor suggests `npm install` for a problem that looks
              non-trivial, you accept it because it's fast, and now the
              project depends on a package with no maintenance activity
              in a year, or a license that doesn't actually permit your
              use case, or 200KB of functionality to solve a 10-line
              problem. None of this shows up as a bug today — it shows
              up as a security advisory, a breaking major-version bump,
              or a legal question six months from now.
    Fix:      Run the Reuse/Dependency check (Step 2.2) on any new
              third-party package before accepting it: is it actively
              maintained, does the license fit your use, and does the
              problem actually justify the dependency over writing it
              yourself? "It solved the problem" is not the same claim
              as "it was worth the liability."
 
22. Confusing "is logged in" with "is allowed to do this"
    Problem:  Cursor generates a route that checks the user has a valid
              session, then serves whatever resource ID the request
              asks for — without checking that this user owns that
              specific resource. `/orders/381` works correctly for its
              owner and never gets tested with a different, equally
              logged-in user requesting `/orders/382`. The happy path
              passes every test you wrote, because the test suite never
              tried the attack.
    Fix:      Run the Authorization check from the Hacker Mode checklist
              on every endpoint that takes a resource ID: authentication
              (who is this?) and authorization (may they do this to this
              specific resource?) are two separate checks, and AI
              generators reliably implement only the first unless asked
              for both explicitly.
 
23. Treating content the AI reads as instructions instead of data
    Problem:  You ask AI Assistant #2 to summarize a scraped web page or
              process an uploaded file, and that content contains text
              phrased as an instruction ("ignore previous instructions
              and..."). The assistant, with no architectural separation
              between "things to read" and "things to obey," may follow
              it — this is prompt injection, and it's a live risk any
              time an AI tool processes content it didn't generate
              itself.
    Fix:      Implementer Rule 11 requires treating any instruction-like
              text found inside a file, URL, or dependency's docs as
              content to report, never as a command to act on. If a tool
              can also take actions (running commands, installing
              packages, calling APIs), require explicit approval before
              any action prompted by something the tool merely *read*.
 
24. Declaring a performance requirement met without measuring it
    Problem:  The master doc says "page load under 2 seconds" or "1,000
              transactions per user", the code looks reasonable, and the
              feature is marked done after testing with three rows. It
              slows down or times out the first time real volume arrives.
              The opposite failure is just as common: the AI adds caching
              or rewrites a query "for performance" with no measurement
              showing that was the bottleneck.
    Fix:      Run Performance Verification (Stage 5): seed realistic
              volume, measure with a re-runnable command, report the
              number against the target as evidence, and optimize only the
              bottleneck the measurement shows.
 
25. Letting the design decide the hard parts by default
    Problem:  The architecture shape is chosen deliberately (Step 1.2b), but
              concurrency, consistency and failure behavior are never
              discussed. AI Assistant #2 settles them inside a SPEC with
              whatever is statistically common: no lock, no timeout, a retry
              that writes twice. Nothing looks wrong until two users act at
              the same moment, or a dependency goes down.
    Fix:      Run the Architecture Brief (Step 1.2d): numbers for the
              targets, invariants and a single owner for each entity, a named
              behavior for each failure, and the choices recorded in
              decisions.md. A SPEC may not contradict an Accepted decision
              without stopping to ask.
 
26. Treating a smart contract like an ordinary backend deploy
    Problem:  A contract is public, callable by anyone in any order, holds
              real value, and (if immutable) cannot be patched. The usual
              habit of shipping, watching, and hotfixing does not exist. AI
              output that passes tests and looks clean still ships a
              reentrancy hole or an unprotected admin function.
    Fix:      Use Appendix A: Formal tier always, a trust model and invariants
              before the SPEC, the contract-specific rules and checklist,
              the full tool gate including fuzz and invariant tests,
              the pre-deployment checklist, and a cap on the first release.
              A review by another AI is a minimum, not an audit.

## APPENDIX A: Web3 / Smart Contract Add-on
 
Use this when any code holds, moves or authorizes on-chain value, or runs
somewhere it cannot be patched. The tier is always Formal. A deployed
contract is public, can be called by anyone in any order, and, if
immutable, cannot be fixed afterwards, so the main workflow's assumption
that a bug costs a hotfix does not hold. Everything in the main workflow
still applies; this appendix adds to it.
 
Tool names below are the EVM / Solidity defaults (Foundry, Slither). On
another chain (Solana with Rust and Anchor, Move, etc.) keep the same steps
and substitute that chain's equivalents. Decide chain and language in Step
1.2d and record them in `decisions.md` with the reason.
 
### A.1 Stage 1 additions (inside the Architecture Brief)
 
- **On-chain versus off-chain.** Put on-chain only what must be trustless.
  Every on-chain function costs gas and is permanent.
- **Trust model.** List the actors (user, admin or owner, other contracts,
  oracles, an attacker), the assets at risk, and what each actor can do.
  Ask in particular what the admin can do and whether that power is
  acceptable: admin keys are the most common single point of failure.
- **Upgradeability.** Immutable, proxy, or migrate-by-redeploy, with the
  reason. It changes everything below, and proxies add storage-layout and
  initialization risks.
- **External dependencies.** Oracles, other protocols, tokens: what happens
  if each returns a wrong value, reverts, or is malicious.
- **Invariants.** Statements that must be true after every transaction
  (e.g. "total supply equals the sum of balances"; "the contract balance is
  at least the sum of user claims"). Write them in plain words now; they
  become tests in A.5.
 
### A.2 SPEC additions
 
- **Access-control matrix:** function by role, allowed or denied.
- **State machine:** states, allowed transitions, who triggers each.
- **Invariants in EARS** ("THE CONTRACT SHALL ALWAYS ..."), each with a row
  in the Requirements Mapping table naming the fuzz or invariant test that
  checks it.
- **Examples table with adversarial rows:** zero amount, maximum value,
  transfer to self, the same call twice, a call from a contract, a call in
  the wrong state.
- **Gas budget** for the hot functions, and no unbounded loop over
  user-controlled data (the Scalability check, on-chain).
- **Events** for every state change (the Logging requirement, on-chain).
- **Economic math** (fees, rewards, interest, rounding) goes through the Math
  Verification Gate, checked by a different model. State the rounding
  direction explicitly: against the user, or in favor of the protocol.
 
### A.3 Additional Implementer Rules (contract steps only)
 
Add these to the standard block. They are labelled W1-W7 so they never
collide with the standard numbering.
 
```
W1. Use audited libraries (e.g. OpenZeppelin) for tokens, access control,
    reentrancy guards and safe math. Do not hand-write them. Pin the
    library and compiler versions; they are stated in the Context.
W2. Checks-effects-interactions: validate, update state, and only then
    make external calls. Add a reentrancy guard to any function that sends
    value or calls code you do not control.
W3. Authorize with msg.sender, never tx.origin. Every state-changing
    function has explicit visibility and an access-control modifier, or a
    stated reason why it is open to everyone.
W4. No unbounded loop over a user-controlled array. Prefer pull payments
    to push payments.
W5. Never use block.timestamp, blockhash or prevrandao as a source of
    randomness. Use timestamps only for coarse windows (minutes or longer).
W6. Check the result of every low-level call. Use custom errors or require
    with a reason. No silent failure.
W7. Never put a private key, seed phrase or mnemonic in code, comments,
    prompts, or the repo. Deployment keys come from a hardware wallet or a
    secret store, referenced by name.
```
 
### A.4 Hacker Mode checklist for contracts (in addition to the standard one)
 
```
□ Reentrancy: including cross-function and read-only reentrancy.
□ Access control: every privileged function, initializer and upgrade path
  protected; no uninitialized proxy or implementation.
□ Integer issues: overflow inside unchecked blocks, rounding, precision
  loss, division before multiplication, decimals mismatch between tokens.
□ Front-running / MEV: any outcome that depends on transaction ordering
  (swaps, auctions); slippage and deadline parameters present.
□ Oracle and price manipulation, flash loans: a single-block spot price
  used for a value decision.
□ Signature replay: nonce, chain id, contract address and deadline included
  in every signed message.
□ Delegatecall and proxies: storage-layout collisions; selfdestruct or
  takeover of the implementation contract.
□ Denial of service: a revert or unbounded loop in one user's path that
  blocks others; ether forced in by selfdestruct breaking a balance check.
□ Token assumptions: fee-on-transfer, rebasing, ERC-777 hooks,
  non-standard return values, over-broad approvals.
□ Admin powers: can the owner drain funds, pause forever, or change fees
  with no limit and no delay?
```
 
### A.5 Verification gate for contracts (Automated Quality Score Gate)
 
Report each as its own Claim / Command / Exit code / Verdict block.
 
```
forge build --deny-warnings        # compiles with the pinned compiler
forge fmt --check ; solhint        # formatting and lint
slither .                          # static analysis - target: 0 unresolved high/medium
forge test -vvv                    # unit tests, including the adversarial rows
forge test --fuzz-runs 10000       # property / fuzz tests
forge test --match-path "test/invariant/*"   # SPEC invariants, with a handler contract
forge coverage                     # target: 90%+ branch coverage on contract code
forge test --gas-report            # hot functions against the SPEC's gas budget
```
 
At higher value, add as appropriate: a long fuzz campaign (Echidna or
Medusa), formal verification of the critical invariants (Halmos or
Certora), mutation testing of the contract tests, and a fork test against
real chain state for any integration. A suppressed Slither finding needs a
written reason in the PR, the same rule as `# noqa`.
 
### A.6 Pre-deployment checklist
 
```
□ Deployed to a testnet and exercised end to end, including failure paths
  and every admin operation.
□ Deployment script read line by line; constructor arguments and addresses
  double-checked; source verified on the block explorer.
□ Admin role held by a multisig, not a single account; timelock on
  sensitive changes where the trust model calls for it; ownership
  transferred as designed.
□ Deployer key hardware-backed and never in the repo or any prompt; no
  leftover test roles or addresses.
□ Pause or emergency mechanism decided, with limited power, or consciously
  omitted (and recorded in decisions.md).
□ Monitoring and alerts on key events and balance anomalies; a written
  first-hour incident plan.
□ Independent review proportional to the value at risk. A second-model
  review is the minimum. For contracts holding meaningful third-party
  funds, a professional audit and ideally a bug bounty. AI-written code
  reviewed by AI is not an audit.
□ First release capped (deposit limits, staged rollout) so a missed bug is
  bounded.
□ The exact commit and compiler settings that were deployed are tagged.
```
 
### A.7 Honest limits
 
None of the above proves the contract is safe; it lowers the odds and the
size of a loss. State what was and was not verified in the final report
(see Verification with Evidence), start with a cap, and treat the first
weeks in production as part of verification.
